# Флоу разработки с помощью Git

Разберём весь путь от постановки задачи до отправки Merge Request на ревью.

<Steps>

### Работа по задачам в Jira

Работа по задачам ведётся в **Jira** — подробную инструкцию по работе с ней
смотри на странице <Link className="underline font-bold cursor-pointer" href="/departments/jira">Jira</Link>.

Пока задача не взята в работу, она лежит в колонке **To Do** либо в
**бэклоге**. Дальше задача двигается по доске вместе с тем, что происходит в
Git и GitLab:

1. Берёшь задачу в работу — переносишь её в **In Progress**.
2. Сделал коммит, открыл MR и передал его на ревью — переносишь задачу в
   **Review**.
3. Получил апрув на MR — переносишь задачу в **Тестирование**, если на
   проекте есть тестировщики.
4. После успешного тестирования дальше задачу по доске двигают уже другие
   отделы (тестировщики, менеджер и так далее).

<Callout type="warning">
  Флоу и названия колонок в Jira могут отличаться от проекта к проекту.
  Обязательно уточняй актуальный процесс у тимлида или проектного менеджера.
</Callout>

### Создание ветки

У каждой задачи в Jira есть свой порядковый номер. Если ветка относится
только к одной задаче, номер добавляется в её название:

```
14535/fix/moscow-disp-request
```

| Часть | Пример | Что означает |
| --- | --- | --- |
| Номер задачи | `14535` | Номер задачи в Jira, к которой относится ветка |
| Тип изменения | `fix` | Что именно делает ветка — тип по общепринятой конвенции (см. таблицу ниже) |
| Описание | `moscow-disp-request` | Коротко, по-английски и через дефис, о сути задачи |

Тип изменения принято выбирать из небольшого набора префиксов:

| Префикс | Когда используется |
| --- | --- |
| `feat/` | Новая функциональность |
| `fix/` | Исправление бага |
| `refactor/` | Рефакторинг кода без изменения поведения |
| `docs/` | Изменения в документации |
| `style/` | Форматирование, стили кода — без изменения логики |
| `test/` | Добавление или изменение тестов |
| `chore/` | Технические задачи, не влияющие на функциональность (обновление зависимостей и т.п.) |
| `perf/` | Изменения, направленные на производительность |
| `hotfix/` | Срочное исправление критичного бага, обычно прямо в проде |

Ветки не должны жить долго: одна задача — одна ветка. Так меньше шанс
получить конфликт кода при мерже.

Бывают исключения — долгоживущие **фича-ветки**, в которые несколько
разработчиков мержат ветки по одной большой фиче. Такое случается, когда на
деве, где тестируется фича, уже лежит другая фича, которую команда готовит к
релизу, и заливать поверх неё ещё непроверенный тестировщиками код нельзя.
Пока фича ждёт своей очереди, в неё сливают все ветки по задачам, а когда в
проекте наступает момент выкатки — мержат в `master` целиком.

Такие ветки можно называть без номера задачи, но название должно говорить
само за себя, например:

```
feature/moscow-health-checkup
```

За актуальностью такой ветки нужно следить и периодически делать
`git rebase` с `master`, чтобы в дальнейшем было меньше конфликтов при мерже.

### Первый коммит

Прежде чем создавать первый коммит и добавлять файлы в индекс Git, нужно
убедиться, что с кодом всё в порядке.

1. Запусти форматтеры и линтеры в терминале и проверь, что всё исправно.
2. Посмотри, какие файлы попадут в коммит, чтобы не утащить туда лишнее —
   например `.env` или файлы, которые не относятся к задаче.

Список изменённых файлов удобно смотреть прямо в IDE — во вкладке
**Source Control** в VSCode или **Git → Local Changes** в WebStorm:

<Image
  src={gitListFiles}
  alt="Список изменённых файлов во вкладке Source Control в VSCode"
  className="mt-4 rounded-lg border border-black/10 dark:border-white/10"
/>

Обычно линтеры и форматтеры запускаются автоматически при `git commit` —
это делает [Husky](https://typicode.github.io/husky/). Но лучше прогнать их
вручную заранее, чтобы точно убедиться, что всё в порядке и не терять время
на исправления уже после коммита.

<Callout type="warning">
  Проверять линтеры и билд локально нужно **обязательно**: при открытии MR
  GitLab тоже прогоняет линтеры и билд в CI, и если пайплайн падает с
  ошибкой, смержить такой MR не получится. Так что лучше найти и исправить
  проблему у себя локально, чем ждать красный пайплайн в GitLab.
</Callout>

Список доступных команд для проверки и форматирования обычно можно
посмотреть в `package.json` в разделе `scripts`:

<Image
  src={gitListCommand}
  alt="Скрипты lint, lint-fix и format в package.json"
  className="mt-4 rounded-lg border border-black/10 dark:border-white/10"
/>

Так выглядит неуспешный запуск линтера — есть ошибка, которую нужно
исправить перед коммитом:

<Image
  src={lintBad}
  alt="Линтер завершился с ошибкой"
  className="mt-4 rounded-lg border border-black/10 dark:border-white/10"
/>

А так — успешный запуск, когда ошибок нет и можно спокойно коммитить:

<Image
  src={lintGood}
  alt="Линтер прошёл без ошибок"
  className="mt-4 rounded-lg border border-black/10 dark:border-white/10"

Когда линтеры и билд прошли успешно, можно создавать и пушить коммит:

```bash
# смотрим, какие файлы изменились
git status

# добавляем нужные файлы в индекс (или git add . — если уверен, что лишнего нет)
git add src/components/DispRequest

# ещё раз проверяем, что в индекс попало именно то, что нужно
git status

# создаём коммит с понятным сообщением
git commit -m "14535: fix moscow disp request"

# первый пуш ветки — с флагом -u, чтобы привязать её к remote
git push -u origin 14535/fix/moscow-disp-request
```

<Callout type="info">
  Флаг `-u` (`--set-upstream`) нужен только при первом пуше новой ветки — он
  связывает локальную ветку с веткой в GitLab. Дальше для этой ветки
  достаточно просто `git push`.
</Callout>

После пуша обновится граф истории коммитов — в нём будет виден твой коммит
и указано, кто его автор:

<Image
  src={gitCommit}
  alt="Граф истории коммитов с новым коммитом и указанием автора"
  className="mt-4 rounded-lg border border-black/10 dark:border-white/10"
/>

<details className="mt-4">
  <summary>Ошибся в коммите, но ещё не запушил — как исправить?</summary>

  Если нужно поправить сообщение коммита или добавить забытый файл, используй
  `--amend` — он заменит последний коммит новым, не добавляя лишний коммит в
  историю:

  ```bash
  # если забыл добавить файл
  git add забытый-файл.tsx

  # правим последний коммит: сообщение и/или состав файлов
  git commit --amend -m "новое сообщение коммита"
  ```
</details>

<details className="mt-4">
  <summary>Как откатить коммит и запушить заново?</summary>

  Если коммит ещё **не запушен**, можно просто откатиться назад:

  ```bash
  # отменяет коммит, изменения остаются в индексе — можно поправить и закоммитить заново
  git reset --soft HEAD~1

  # отменяет коммит и полностью отбрасывает изменения
  git reset --hard HEAD~1
  ```

  Если коммит уже **запушен** и его нужно откатить и в GitLab, после
  `git reset` потребуется принудительный пуш:

  ```bash
  git push --force-with-lease
  ```

  <Callout type="warning">
    Force push переписывает историю ветки — используй его только в своей
    личной ветке и никогда в `master`. Если кто-то из коллег уже успел
    зафетчить эту ветку, обязательно предупреди его.
  </Callout>
</details>

### Открываем Merge Request

Когда ветка готова, открываем Merge Request в GitLab и описываем, что было
сделано.

**Название и описание.** Название MR обычно повторяет суть коммита. В
описании подробно рассказываем, что было сделано и почему — чем подробнее
описание, тем проще ревьюеру понять контекст. Также в описание нужно
добавлять ссылки на задачи, которые были выполнены в этом MR.

<Image
  src={mrDescription}
  alt="Форма создания Merge Request в GitLab: заголовок и описание"
  className="mt-4 rounded-lg border border-black/10 dark:border-white/10"
/>

<Callout type="warning">
  Привязка задач к MR в будущем станет обязательной, но пока что на
  некоторых проектах это опционально — уточняй у тимлида, как принято
  именно на твоём проекте.
</Callout>

**Ревьюер.** В GitLab можно сразу выбрать, кто будет проверять твой MR —
поле **Reviewer** (или **Assignee**, если ревью на проекте назначают через
него):

<Image
  src={assigneeReview}
  alt="Выбор ревьюера в Merge Request в GitLab"
  className="mt-4 rounded-lg border border-black/10 dark:border-white/10"
/>

**Опции мержа.** Перед созданием MR стоит сразу отметить два чекбокса:
удалять ветку-источник после мержа и сквошить коммиты при принятии MR — это
не даёт истории `master` засоряться промежуточными коммитами вроде «fix
typo» или «wip»:

### Проверяем и отправляем на ревью

Перед тем как звать кого-то на ревью, убедись, что все проверки в GitLab CI
прошли успешно (пайплайн зелёный). После этого отправляй MR своему тимлиду на
проекте на проверку.

<Callout type="warning">
  MR не должен содержать в себе тысячи строк кода. Он должен быть небольшим
  и понятным, чтобы другому разработчику было удобно его проверять. **MR
  больше 1000 строк автоматически отклоняется на код-ревью.**
</Callout>

обычно настроен **Telegram-бот**, который сообщает в рабочий чат о новых
выкатках на дев и прод — с версией релиза и списком изменений:
