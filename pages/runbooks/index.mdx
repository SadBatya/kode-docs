# Runbooks

Пошаговые инструкции для повторяющихся операций и восстановления после сбоев.

<Callout type="info">
  Runbook должен быть выполним **с нуля** человеком, который не работал с этой системой. Пишите команды, а не абстрактные описания.
</Callout>

## Доступные runbooks

| Runbook | Когда использовать | Отдел |
|---------|--------------------|-------|
| [Rollback деплоя](/engineering/devops/deployment#откат-rollback) | Деплой сломал prod | DevOps |
| [Перезапуск сервиса](#перезапуск-сервиса) | Сервис завис / не отвечает | DevOps |
| [Очистка очереди Kafka](#kafka) | Очередь переполнена | Backend |
| [Ротация секретов](#ротация-секретов) | Плановая / после утечки | DevOps |
| [Масштабирование под нагрузкой](#масштабирование) | High traffic event | DevOps |

## Перезапуск сервиса

**Когда:** сервис не отвечает на health-check, но поды в статусе Running.

```bash
# Проверить статус
kubectl get pods -n production | grep <service-name>
kubectl describe pod <pod-name> -n production

# Rolling restart (без downtime)
kubectl rollout restart deployment/<service-name> -n production

# Следить за статусом
kubectl rollout status deployment/<service-name> -n production
```

**После:** убедитесь, что error rate в Grafana вернулся к норме.

## Kafka

### Очистка застрявших сообщений

```bash
# Посмотреть lag consumer groups
kubectl exec -it kafka-0 -n infra -- \
  kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --all-groups

# Сбросить offset (ОПАСНО — сообщения будут пропущены)
# Сначала остановите consumer
kubectl scale deployment/notification-service --replicas=0 -n production

# Сбросить offset на конец очереди
kafka-consumer-groups.sh \
  --bootstrap-server kafka:9092 \
  --group notification-group \
  --topic notifications \
  --reset-offsets --to-latest --execute

# Запустить consumer обратно
kubectl scale deployment/notification-service --replicas=2 -n production
```

## Ротация секретов

```bash
# 1. Сгенерировать новый секрет
openssl rand -base64 32

# 2. Обновить в Vault
vault kv patch secret/backend/prod DATABASE_PASSWORD="new-password"

# 3. Перезапустить сервисы, использующие секрет
kubectl rollout restart deployment/user-service -n production

# 4. Убедиться, что старый секрет деактивирован в источнике
```

## Масштабирование

### Ручное масштабирование перед запланированной нагрузкой

```bash
# За час до события увеличьте replicas
kubectl scale deployment/api-gateway --replicas=10 -n production
kubectl scale deployment/user-service --replicas=8 -n production

# Наблюдайте за HPA
kubectl get hpa -n production -w

# После события верните к норме
kubectl scale deployment/api-gateway --replicas=3 -n production
```

## Шаблон нового runbook

Добавляя новый runbook, используйте этот шаблон:

```markdown
## Название операции

**Когда:** [условие, при котором нужен этот runbook]
**Влияние:** [что может пойти не так при неправильном выполнении]
**Требуется:** [нужные доступы / инструменты]

### Шаги

1. Первый шаг с командой
2. Второй шаг
3. Проверка результата

### Возможные проблемы

| Симптом | Решение |
|---------|---------|
| ... | ... |
```
