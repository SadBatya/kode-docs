# Реагирование на инциденты

<Callout type="warning">
  **При инциденте:** сначала стабилизация (откат/mitigation), потом разбор причин.
</Callout>

## Уровни критичности

| Уровень | Описание | Примеры | Response Time |
|---------|----------|---------|---------------|
| **P0** | Production полностью недоступен | Сайт не открывается, оплаты не проходят | 15 мин |
| **P1** | Критичная функция нарушена | Нельзя залогиниться, ошибки у >10% пользователей | 30 мин |
| **P2** | Деградация функциональности | Медленные ответы, функция доступна частично | 2 часа |
| **P3** | Минорная проблема | Косметический баг, не влияет на бизнес | Следующий sprint |

## P0 / P1: Процедура реагирования

<Steps>
### Объявите инцидент

Напишите в `#incidents`:
```
🚨 INCIDENT P0 | [Краткое описание]
Начало: 14:35
On-call: @username
Влияние: оплаты недоступны ~5 мин
Статус: расследуем
```

### Назначьте роли

- **Incident Commander (IC)** — координирует, принимает решения
- **Tech Lead** — ведёт техническое расследование
- **Communicator** — обновляет статус-страницу и уведомляет стейкхолдеров

### Стабилизируйте систему

Приоритет — восстановить работу, даже если не понимаем причину:

```bash
# Откат деплоя
kubectl rollout undo deployment/service-name -n production

# Включить feature flag, обходящий проблемный код
# Увеличить replicas при проблемах с нагрузкой
kubectl scale deployment/service-name --replicas=5 -n production
```

### Коммуницируйте статус

Обновляйте `#incidents` каждые 15 минут (P0) или 30 минут (P1):
```
🔄 UPDATE 14:50 | Откатили деплой v2.3.1 → v2.3.0. Мониторим...
✅ RESOLVED 15:05 | Сервис восстановлен. Ошибки вернулись к норме.
```

### Проведите post-mortem

В течение **48 часов** после инцидента. Шаблон ниже.
</Steps>

## Post-Mortem шаблон

```markdown
## Post-Mortem: [Название инцидента]

**Дата:** YYYY-MM-DD
**Длительность:** X минут
**Уровень:** P0 / P1
**Затронуто пользователей:** ~N

### Что произошло (Timeline)

| Время | Событие |
|-------|---------|
| 14:30 | Деплой v2.3.1 |
| 14:35 | Первый алерт: error rate > 5% |
| 14:40 | Начало расследования |
| 14:55 | Откат деплоя |
| 15:05 | Восстановление |

### Первопричина (Root Cause)

[Техническое объяснение что пошло не так]

### Что сработало хорошо

- Алерты сработали быстро
- Откат занял < 5 мин

### Что можно улучшить

- Не было канary-деплоя
- Тест на staging не покрывал этот кейс

### Action Items

| Задача | Ответственный | Срок |
|--------|--------------|------|
| Добавить canary deployment | @devops | 2024-02-15 |
| Написать тест на regression | @backend | 2024-02-10 |
```

## Дежурство (On-Call)

<Tabs items={['Расписание', 'Алерты', 'Эскалация']}>
  <Tabs.Tab>
    - Ротация раз в неделю (Пн → Пн)
    - Расписание: [PagerDuty](https://kode.pagerduty.com)
    - Смена начинается в 10:00 Мск
    - Backup on-call назначается автоматически

    **Ожидания от on-call:**
    - Ответить на алерт в течение 15 минут (P0/P1)
    - Быть доступным по телефону в рабочее время
    - Знать как выполнить базовый rollback
  </Tabs.Tab>
  <Tabs.Tab>
    Алерты приходят через PagerDuty → звонок на телефон.

    **Каналы алертов:**
    - `#alerts-prod` — все prod-алерты
    - `#alerts-staging` — staging-алерты (не требуют немедленной реакции)

    **Не все алерты = инцидент.** Оцени:
    1. Это реальная проблема или flapping?
    2. Пользователи затронуты?
    3. Нужна ли помощь?
  </Tabs.Tab>
  <Tabs.Tab>
    Если не можете решить за 30 минут — эскалируйте:

    1. Тимлид своего отдела
    2. DevOps-тимлид
    3. CTO (только P0, если тимлиды недоступны)

    Не стесняйтесь эскалировать — лучше разбудить коллегу, чем терять пользователей.
  </Tabs.Tab>
</Tabs>
