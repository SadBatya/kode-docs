# Code Review

Код-ревью — это не проверка, это совместное улучшение кода. Цель: поделиться знаниями, поймать ошибки и поддержать качество кодовой базы.

## Требования к MR

- **Минимум 1 approve** от члена команды (кроме автора)
- **Все CI проверки** должны пройти (тесты, линтер, typecheck)
- **Нет неразрешённых тредов** в обсуждении
- **Размер MR:** не более 400 строк diff (исключение — автогенерированный код)

<Callout type="info">
  Большой MR? Разбейте на части. Небольшие MR ревьюятся быстрее и качественнее.
</Callout>

## Для автора MR

<Steps>
### Подготовьте MR

- Заполните описание: **что** изменилось и **почему**
- Добавьте ссылку на задачу в Jira/Linear
- Если нужно — добавьте скриншоты или видео для UI-изменений

### Назначьте ревьюеров

- Минимум 1 человек из вашей команды
- Для кросс-командных изменений — добавьте ревьюера из затронутой команды

### Ответьте на комментарии

- Отвечайте на все комментарии — даже если согласились и сделали правку
- Спорные вопросы решайте синхронно (Slack, звонок), итог фиксируйте в треде

### После approve — сами мёрджите

Автор отвечает за своё изменение. Мёрджите сами после получения approvals.
</Steps>

## Для ревьюера

### Что проверять

**Корректность:**
- Логика соответствует задаче
- Edge cases обработаны
- Нет race conditions (в Go — run with `-race`)

**Безопасность:**
- Нет SQL-инъекций, XSS, exposed secrets
- Авторизация проверяется там где нужно
- Входные данные валидируются

**Качество:**
- Код читаем без дополнительных объяснений
- Нет дублирования логики
- Тесты покрывают критичные пути

**Производительность:**
- Нет N+1 запросов
- Индексы там, где нужны
- Нет лишних аллокаций в hot path

### Тон комментариев

Используйте **Conventional Comments**:

```
# Блокирующее — должно быть исправлено
blocking: Это создаёт SQL-инъекцию. Используй параметризованные запросы.

# Неблокирующее — на усмотрение автора
nit: Можно использовать errors.Is вместо == для сравнения ошибок.

# Вопрос — хочу понять
question: Почему здесь используется мьютекс, а не channel?

# Предложение
suggestion: Рассмотри использование sync.Map — меньше boilerplate.

# Похвала
praise: Отличное решение! Раньше это было намного сложнее.
```

### SLA ревью

| Размер MR | Ожидаемое время |
|-----------|-----------------|
| < 50 строк | 2 часа |
| 50–200 строк | полдня |
| 200–400 строк | 1 рабочий день |

<Callout type="warning">
  Если ревью затягивается — напомните в `#team-<отдел>`. Не стесняйтесь просить коллег.
</Callout>

## Чек-лист автора

Перед нажатием «Ready for review»:

- [ ] Я сам прочитал свой diff полностью
- [ ] Удалены все `console.log` / `fmt.Println` / debug-код
- [ ] Нет захардкоженных секретов или URL окружений
- [ ] Тесты написаны и проходят
- [ ] `CHANGELOG` обновлён (если применимо)
- [ ] Описание MR объясняет **зачем**, а не только **что**
